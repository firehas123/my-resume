# Muhammad Hassan Chattha: resume and portfolio

My personal site, built with Next.js (App Router, TypeScript), plain CSS Modules
with CSS variables, Motion for scroll and hover animation, and a canvas dot field
in the hero.

What it does: eight languages (English and German as working languages), projects
pulled from GitHub every day, a contact form with a captcha, its own cookie-free visit
statistics with a weekly backup, a downloadable CV in every language, and dark and
light themes.

## Commands

| Command         | What it does                                                                 |
| --------------- | ---------------------------------------------------------------------------- |
| `npm install`   | Install dependencies (once, and after pulling changes to `package.json`).    |
| `npm run dev`   | Development server on port 3000, reachable from other devices on the network. |
| `npm run build` | Production build (this is what Vercel runs).                                  |
| `npm run start` | Serve the production build locally.                                           |
| `npm run sync`  | Refresh `src/data/projects.json` from GitHub (needs the `gh` CLI, logged in). |
| `npm run cv`    | Build one CV per language (`public/files/cv-<code>.pdf`) from `profile.json`. Runs before every build and dev start. |
| `npm run i18n:check` | List texts missing or identical to English, per language.              |
| `npm run i18n:add`   | After adding a language code: create its messages file, check its fonts. |
| `npm test`      | Run all unit tests: tab rules, languages, right-to-left text, contact form, stats backups. |
| `npm run stats:backup` | Back up the statistics by hand (normally the weekly workflow does it). |
| `npm run stats:restore <file>` | Load such a backup into an empty statistics database.          |
| `npm run lint`  | Check the code with ESLint.                                                   |

Requires Node.js 20.9 or newer.

### Preview on another device (for example a Mac on the same Wi-Fi)

`npm run dev` listens on all network interfaces. Open `http://<this machine's IP>:3000`
on the other device, for example `http://192.168.0.67:3000`. If the IP changes,
also update `allowedDevOrigins` in `next.config.ts`.

## Common changes

### Update my details

Edit `src/data/profile.json`. Open items that still need my input are listed in
`TODO.md`.

- **The CVs** are built from the same data as the site, one per language, before every
  build (`npm run cv` to do it by hand). No phone number; an email address only if
  `"cvShowEmail": true` and `"cvEmail"` is set, the photo only if `"cvShowPhoto": true`.
  A file `public/files/europass-cv-<code>.pdf`, if you add one, is offered in the
  download menu as "Europass format".
- **Show or hide a profile link:** set `"show": true` or `false` on the link (Fiverr is
  currently `false`).

### Languages

Every page exists in every language, under its code: `/en/...`, `/de/...`, `/ar/...`.
The bare address sends a first-time visitor to the language of their browser (English
if it is not offered) and afterwards to the language they picked in the menu.

- **The one list** is `"languages"` in `src/i18n/languages.json`. `"primary"` are the
  languages I work in; every other language shows a note that it was translated
  automatically, and its CV says so too. `"legal"` are the languages the legal pages
  exist in; the others link to English.
- **Add a language:** put its code in `"languages"` (it needs an entry in `"catalog"`:
  pt, pl, ur, hi, zh and ja are already there), then run `npm run i18n:add`. That creates
  `messages/<code>.json` (empty, so the site shows English until it is translated) and
  checks the fonts. Then translate: the interface in `messages/<code>.json`, my texts
  in `src/data/profile.json`, project summaries in `src/data/overrides.json`.
  `npm run i18n:check` lists what is still missing. Scripts other than Latin and Arabic
  (Hindi, Chinese, Japanese) also need a website font in `src/i18n/fonts.ts`.
- **Remove a language:** delete its code from `"languages"`. Nothing else is needed.
- **Right to left** (ar, ur) is automatic: the layout mirrors through logical CSS
  properties, while numbers, code terms and logos stay left to right.
- Never translate names, companies, schools, repo names or established technical terms
  (Backend, Microservices, Docker, CI/CD, Machine Learning).

### Refresh projects from GitHub

```bash
npm run sync      # rewrites src/data/projects.json and SYNC-REPORT.md
npm test          # optional: checks the grouping rules still behave
git add src/data/projects.json SYNC-REPORT.md && git commit -m "chore: sync projects" && git push
```

The sync prints a table of every repo with its top languages, the group it was put in
and why, plus a list of skipped forks. The same is saved to `SYNC-REPORT.md`, so you can
check the result before committing.

#### Automatic daily sync (GitHub Actions)

You usually don't need to run the sync yourself. The workflow
`.github/workflows/sync-projects.yml` runs it **every day at 04:17 UTC**. It reads
your public repos with the workflow's own built-in token, so no secrets are needed.
If `src/data/projects.json` or `SYNC-REPORT.md` changed, it commits them to `main`
as *github-actions[bot]*, together with any README images. That push starts the
Vercel deployment. If nothing changed, it makes no commit. The sync rules are the
same as for a local run: private repos never appear, and `overrides.json` always wins.

To run it by hand (for example right after creating a new repo):

1. Open the repository on GitHub and click the **Actions** tab.
2. Choose **Sync projects** in the list of workflows on the left.
3. Click **Run workflow** on the right, keep the branch on `main`, and click the green
   **Run workflow** button.
4. After a minute or two the run shows a green tick. Open it and expand
   **Commit and push if anything changed**. That step either says "No changes; nothing
   to commit." or shows the commit it pushed.

A sync commit lands on `main` on GitHub, so run `git pull` before your next local
change. Two details keep the daily run quiet: the report's date only changes when its
content changes, and a repo's "last updated" date ignores the workflow's own commits.

Which repos are shown:

- **Private repositories never appear**, not on the site and not in the report.
- **Empty repositories** are skipped.
- **Forks** are shown only if my copy has **commits of my own** that the original does
  not have. The sync compares my default branch with the original's (GitHub's "ahead
  by" count). Forks without my own commits stay hidden. Shown forks get a small
  **Fork** label on the card, and their project page says "Fork of owner/repo".
  `overrides.json` can force either way with `"include": true` or `"hide": true`.
  `SYNC-REPORT.md` lists every skipped fork and why.
- A fork keeps the original's description and website until you change them on GitHub.
  While they are still identical to the original's, they describe the original, not your
  work, so they are not shown. Add a `summary` or `demo` in `overrides.json`, or edit the
  fork's description on GitHub.
- A repo's GitHub "Website" field becomes its **Live demo** link.
- Each repo's **README** is read too. Its first real paragraph becomes the card summary
  when the repo has no GitHub description; its opening sections (intro, features…,
  without badges, raw HTML and install/usage/licence boilerplate) become the overview on
  the project page. READMEs left exactly as a generator wrote them (Create React App,
  Next.js, Vite) are ignored, and so is a fork's README while it is identical to the
  original's.
- The first meaningful **README image** (not a badge) is downloaded to
  `public/projects/readme/` and used as the preview. Projects without one get a
  generated abstract tile (dots and lines from the repo name, in the site's colours).
  A manual screenshot in `public/projects/` always wins.

### How projects are grouped into tabs

GitHub labels every repo with one "primary language", which is often misleading (a
notebook project is "Jupyter Notebook", a web app is often "HTML"). So the sync looks at
each repo's **full language breakdown** instead:

1. **Ignore what isn't project code**: HTML, CSS, SCSS, Makefile, CMake, Dockerfile,
   Shell, Batchfile, TeX and similar.
2. **Merge related languages**:
   - Jupyter Notebook counts as **Python**
   - C and C++ form **C / C++**
   - JavaScript and TypeScript form **JavaScript / TypeScript**
3. The group with the **largest share** of the remaining code wins. A tie goes to the
   group that comes first in the tab order.
4. If nothing is left after step 1 (for example an HTML-only site), the repo goes to
   **Other**.
5. A `"group"` set in `overrides.json` **always wins** over the automatic choice.

Any other language becomes its own group (for example Java, or Go), but it only gets
its own **tab** if it is a mainstream programming language or has at least two
projects; otherwise its projects go under **Other** (the list and the minimum are in
`src/data/language-groups.json`). There is one tab for every group that has at least
one project. Tab order: **C / C++, Python, Java,
JavaScript / TypeScript**, then any others A–Z, and **Other** last. Groups without
projects get no tab.

The rule lists (ignored languages, merges, tab order) live in
`src/data/language-groups.json`, so you can adjust them without touching code. The
logic is in `scripts/lib/grouping.mjs`, with tests in `scripts/grouping.test.mjs`
(`npm test`).

Each project card shows its group plus its top two or three languages as small labels.
The project page shows the same, with percentages.

### Change a project without touching GitHub

Add an entry to `src/data/overrides.json`, keyed by the exact repo name:

```json
{
  "Advanced-Account-Management-System": {
    "title": "Account Management System",
    "summary": "One line about what it does.",
    "group": "C / C++",
    "demo": "https://example.com",
    "featured": true,
    "order": 1
  },
  "made-project-ws2024": { "include": true },
  "SLU": { "hide": true }
}
```

All fields are optional:

| Field | What it does |
| --- | --- |
| `hide` | `true` keeps the repo off the site. |
| `include` | `true` always shows a **fork**, even without commits of my own. Run `npm run sync` after changing it. |
| `group` | The tab to show it under. Any name works, for example `"Python"` or `"C / C++"`. Always wins. |
| `title`, `summary` | Replace the title (repo name with dashes as spaces) or the GitHub description. Plain text, or one text per language: `{ "en": "...", "de": "..." }`. A language without its own text shows English with an "In English" label. |
| `demo` | A Live demo URL, or `null` to remove GitHub's. |
| `featured`, `order` | Featured projects come first, then lower `order`, then the most recently updated. |

### Add a longer write-up to a project page

Create `content/projects/<exact-repo-name>.md` with normal Markdown.

### Add a project picture

1. Take a screenshot of the project running (a real one: the app in use looks better than
   an empty start screen).
2. Name it **exactly like the GitHub repository**, same capitals and dashes, and put it
   in **`public/projects/`**: for example `public/projects/Dots-Game.png`. `.png`, `.jpg`
   and `.webp` all work.
3. Commit and push. The picture appears on the project's card and its page by itself;
   nothing else needs to change.

**Size and framing:** about **1800 × 900 px** (2:1). The card shows a wide strip of the
picture and the project page a slightly taller one, so keep the important part in the
**middle 70 %** with plain margin around it. `public/projects/Dots-Game.png` is an
example: the game is centred on a white canvas, so neither view cuts it off.

**Without a picture,** the card uses the first image in the repository's README, and if
there is none either, a dot-pattern tile drawn by the site. To replace a picture, save
the new file under the same name. (While testing locally, delete `.next/cache/images`
if the old picture still shows.)

### Company logos

The strip shows the official logos in `public/logos/` (`zertificon.svg`, `careem.png`,
`i2c.svg`, `infotech.png`). Where each one came from is recorded in
`public/logos/SOURCES.md`. Each logo is shown as a single-colour silhouette (light on
dark, dark on light), and its company name is the accessible label. If a file is
missing, the name is shown as text instead.

The logos are sized so their **letters** come out the same height, not their boxes.
Zertificon's file includes a tagline under the name, so its box is taller.
`letterRatio` in `profile.json` (under `companies`) says how much of each file's
height the letters fill; adjust it if you replace a logo.

The strip rolls continuously at one steady speed and nothing a visitor does stops or
slows it. While it rolls, each logo is pushed gently away from a nearby cursor and
floats back (a subtler version of the skills cloud's effect). It only stands still,
with no push, for visitors who have "reduce motion" switched on.

### Skill logos

Each pill in "What I work with" shows the technology's logo from
[Devicon](https://devicon.dev) (MIT licence, installed through npm as `devicon`).
Which logo a skill uses is set by `"logos"` on that skill in `profile.json`, using
Devicon's file names, for example `"logos": ["java-plain"]` or two for a combined pill
like C/C++. Browse the names in `node_modules/devicon/icons/`. Skills without a Devicon
logo (JavaFX, InformixDB, Data Structures & Algorithms) have no `logos` and stay text
only.

The logos are drawn in the pill's text colour and turn the technology's brand colour on
hover. A brand colour that would be hard to see on the pill (below 3:1 contrast, such as
black Kafka on a dark pill or yellow JavaScript on a white one) is skipped, and that
logo keeps the text colour.

### Contact form

The form on `/contact` works in one of two ways (`src/lib/contact.ts` decides, from the
environment variables). Either way your email address never appears in the site or its
source, every email names the language the visitor wrote in, and its reply-to is the
visitor's address, so replying in Gmail answers them directly.

**Web3Forms (the default, nothing to set up).** The visitor's browser posts the message
to [Web3Forms](https://web3forms.com), which emails it to you. The access key is
`"contactAccessKey"` in `src/data/profile.json` (`NEXT_PUBLIC_WEB3FORMS_KEY` overrides
it). The form requires an hCaptcha check with Web3Forms' shared key, but Web3Forms
itself still accepts submissions that leave the captcha out (tested 2026-10-07), so a
bot that posts to Web3Forms directly gets through.

**Server check (recommended, needs two free accounts).** The form posts to this site's
`/api/contact`, which asks hCaptcha whether the answer is genuine before anything is
sent, then delivers the email through [Resend](https://resend.com). Nothing can skip the
check, the page no longer contains any key that sends mail, and at most 30 messages a day
get through (one shared counter in the statistics database; nothing about the sender is
stored). To switch it on:

1. [hCaptcha](https://dashboard.hcaptcha.com/signup): create a free account, add a site
   for your domain, and copy its **site key** and your account **secret key**.
2. [Resend](https://resend.com/signup): create a free account **with the Gmail address
   messages should go to**, and create an API key. (Without a domain of your own, Resend
   only delivers to the address the account was created with, which is exactly what
   this needs.)
3. Vercel → Settings → Environment Variables (Production), add:
   `NEXT_PUBLIC_HCAPTCHA_SITEKEY`, `HCAPTCHA_SECRET`, `RESEND_API_KEY` and
   `CONTACT_TO_EMAIL` (that Gmail address). Optional: `CONTACT_FROM_EMAIL` once you
   have a verified domain in Resend.
4. Redeploy, send yourself a test message, then delete the old access key in the
   Web3Forms dashboard (it is public in this repo's history).

Until all four variables are set, the site keeps using Web3Forms and `/api/contact`
answers "off". The privacy policy describes whichever way is active.

### Visitor statistics

The site has three kinds of measurement, all only on the production deployment
(never in previews or local development):

- **Vercel Web Analytics** and **Speed Insights**: switched on in the Vercel dashboard,
  viewed there.
- **The site's own visit counter**, viewed at **`/stats`** (unlisted: `noindex`, not in
  the sitemap, not linked unless `"showStatsLink": true` in `profile.json`).

How the counter works:

- A **visit** is one full load of the site in a browser tab; a **page view** is every
  page looked at. They are told apart in the page's memory, with no cookies and no
  browser storage.
- Only aggregated numbers are stored in Upstash Redis: per day, per day and country,
  all-time totals, hour of day and weekday (Berlin time), pages, site language, device
  type, referring domain, theme, CV downloads per CV language and link clicks, plus the
  last 25 views as country, page and time. The key layout is documented at the top of `scripts/lib/stats-store.mjs`.
- Nothing ever expires and old days are never deleted.
- Never stored: IP addresses, user agents, identifiers, cities or coordinates. Visitors
  sending Do Not Track or Global Privacy Control, bots and automated browsers are not
  counted.
- **Exclude your own visits:** open `/stats?exclude-me=1` once in each browser you use.
  `/stats?exclude-me=0` undoes it.

**Connect the database:** in Vercel open the project → **Storage** → **Create
Database** → **Upstash (Redis)** → connect it to this project, then **redeploy**. The
integration adds `KV_REST_API_URL` and `KV_REST_API_TOKEN`; the code also accepts
`UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN`. Until then `/stats` says
"not connected yet" and nothing is counted.

**Backups run by themselves.** Every Monday the "Stats backup" workflow
(`.github/workflows/stats-backup.yml`) downloads the complete statistics from the
site's public export route and commits them to the separate **`stats-backup`** branch
as `data/stats-backup/<date>.json` (every week is kept) plus `latest.json` (always the
newest). It uses no database credentials and no secrets. If the route is unreachable
or returns anything incomplete, empty, or smaller than the last backup, the run fails
and saves nothing. Start it by hand any time: GitHub → Actions → "Stats backup" →
"Run workflow". Pushes to `stats-backup` never deploy (`vercel.json`).

**Restore** (only into an EMPTY database; needs the database variables locally):

```bash
npx vercel env pull .env.local     # once: copies the database variables locally
git fetch origin stats-backup
git show origin/stats-backup:data/stats-backup/latest.json > /tmp/stats-latest.json
npm run stats:restore /tmp/stats-latest.json
```

Use a date instead of `latest` for an older backup. `npm run stats:backup` still writes
a backup by hand to `data/stats-backup/<date>.json` (see `data/stats-backup/README.md`).

The `/stats` page also has "Download data" buttons (JSON with everything, or CSV with
one row per day and country).

### Change the accent colours

Both accents are defined once, at the top of `src/app/globals.css`:

```css
--accent-bright: #5be3a8; /* dark theme and the black bands */
--accent-deep: #0b7a54;   /* light theme and the light Experience band */
```

Change either line and everything that uses the accent follows, including the hover
shade, which is mixed from it automatically. Keep the deep accent dark enough for
4.5:1 contrast on `#F7F7F8`.

## Deployment

Vercel builds the site with its default Next.js settings. `vercel.json` pins the
framework and turns deployments off for the `stats-backup` branch. Every push to `main`
deploys to production; pushes to other branches get their own preview address and leave
the live site alone. See REVIEW.md, "Publishing", for the first-time setup.

**Working on something bigger:** do it on a branch, check it on that branch's preview
address, and merge into `main` only when it is finished. That keeps half-done work off
the live site.

**New repositories:** keep them private while you work on them. Private repos never
appear on the site; the day one is made public, the daily sync adds it to the projects.
Before making one public, give it a README (its first paragraph and first image become
the card), a short description on GitHub, and make sure no secret was ever committed.
